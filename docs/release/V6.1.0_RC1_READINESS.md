This document is the release gate. A candidate is not a final release until
every required gate is supported by a fresh CI run and an author decision where

preserved.

## 1. Candidate scope

The v6.1 candidate addresses code and claim issues found during a direct review
of the v6.0 repository:

- bounded pending-message count and aggregate shard memory;
- per-message shard-storage and message-size limits;
- explicit resource-limit rejection;
- common authenticated generation time and deadline across a message's shards;
- rejection of conflicting duplicate shard contents and inconsistent metadata;
- bounded delivered-message history with fail-closed behaviour at capacity;
- no u32 message-ID wrap within a session;
- wire-level fragment count limited to 255 because the current fragment header
  stores n in a u8;
- a periodic `Receiver.expire_due()` API plus lazy expiry during receive;
- AONT documentation corrected to mark the general security proof as open.

No old experiment result is overwritten or regenerated by these code changes.

## 3. Mandatory release gates

### Gate A — correctness and bounded resource use

- [ ] Candidate CI passes on the exact candidate head.
- [ ] Future-dated authenticated generation timestamps are rejected beyond the configured clock-skew allowance.
- [ ] All new pipeline regression tests pass.
- [ ] Full existing test suite passes without skipped or masked failures.
- [ ] `verify_all.sh --smoke` exits zero.
- [ ] Receiver integration calls `expire_due()` on a periodic timer.
- [ ] Deployment limits are selected from an explicit workload and memory budget.
- [ ] Session rotation is performed before delivered-ID capacity is exhausted.
- [ ] Sender and receiver use the same maximum message size and fragment policy.

### Gate B — cryptographic assurance

- [ ] A qualified reviewer examines the complete AGP/1 handshake and record
  protocol, including transcript binding, suite negotiation, Finished MACs,
  hybrid secret combination, key updates and replay handling.
- [ ] A formal protocol model or a documented independent analysis is completed.
- [ ] AONT general security theorem remains withdrawn until a correct reduction
  covers all shard placements and adversary views.
- [ ] No claim of information-theoretic security, zero leakage or formal
  verification is made without proof.

### Gate C — empirical validity

- [ ] Existing raw results and registered experiments remain unchanged.
- [ ] New experiments are registered before execution and retain failed runs.
- [ ] Timing results are labelled x86-64 VM measurements.
- [ ] Traffic-analysis null results include confidence intervals and minimum
  detectable effect; no indistinguishability claim is inferred.
- [ ] CAP is described as an EWMA-based adaptation policy, not a superior
  detector.
- [ ] The IEC 62351 comparator is described as a simplified style baseline,
  not a conformant IEC implementation.
- [ ] The IEEE 14-bus study is described as a simulation, not a general safety
  proof or field validation.

### Gate D — manuscript and release integrity

- [ ] Every manuscript number maps to `results/paper_values.json` or a
  documented configuration/definition.
- [ ] Every figure maps to committed raw results and a source script.
- [ ] Every reference is bibliographically verified.
- [ ] All reviewer comments are answered in the response letter.
- [ ] Authors, affiliations, funding and corresponding author are confirmed.
- [ ] Target journal template and data/code policy are checked.
- [ ] Licence and redistribution permissions are explicitly approved.
- [ ] Final tag points to the exact verified candidate commit.
- [ ] Release notes state limitations and reproduce commands.

## 4. Reproduction commands

Use the pinned environment in `requirements.txt` and the repository's Python
3.13 CI container.

```bash
python3 -m compileall -q aegis_pq baselines experiments
python3 -m pytest -q -p no:cacheprovider
./scripts/verify_all.sh
./scripts/verify_all.sh --smoke
```

The full experiment suite is not equivalent to the smoke suite. Timing
experiments should be repeated on a documented machine; stochastic results
should be reproduced from their registered seeds and configurations.

## 5. Versioning and tag policy

The candidate branch is not itself a release tag. The existing v6.0 tag and
historical refs must not be moved or force-updated. A final tag such as
`v6.1.0` may be created only after all mandatory gates pass and the author
approves the release. If the GitHub integration cannot create tag refs, the
author must create the annotated tag from the verified commit in GitHub or git.

## 6. Known non-goals for this candidate

This candidate does not claim to deliver:
- a formal proof of the custom AGP/1 protocol;
- a general AONT security theorem;
- an IEC 62351-conformant implementation;
- RTU/IED/microcontroller performance measurements;
- protection-class 3 ms suitability;
- a general plant invariant-set or safety proof;
- resistance to endpoint compromise, clock compromise or link-saturating DoS.
